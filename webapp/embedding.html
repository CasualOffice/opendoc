Embed the editor

Phase 1 of the SDK ships three things a host can use today: an installable package, a framework-free <opendoc-editor> custom element, and a capability contract that is resolved before the frame's first navigation — so an embed cannot be talked out of the mode it was given. What it does not ship yet is at the bottom of this page, in as many words.

Everything below is extracted from code in this repository by webapp/tools/build-embed-docs.mjs, and a guard fails the build if the page and the code disagree. Each code panel's caption names the file it came from. That is not decoration: the public pages here have carried fabricated claims twice, in both directions, so no example on this page is typed and trusted — see how this page is kept honest.

Install it

@casualoffice/opendoc-embed version 0.1.0: 6 files, 37 kB unpacked, 0 runtime dependencies. Nothing publishes it to a registry yet, so today a host installs the tarball npm pack produces from a checkout. The packaging guard does exactly this — it packs the package, installs the tarball into an empty project, and imports it by its bare specifier, so "installable" is a measured fact rather than a manifest that looks right.

The package is the mount and the capability contract; it does not carry the engine. You also serve the editor's own static files (editor.html and the WebAssembly bundle beside it) from somewhere you control, and point editor-src at them.

Mount it

The element takes 3 attributes and no configuration object. This is the package's own documented usage, and a guard checks every attribute in it against the attributes the element really reads, and the mode value against the names the authority really accepts:

packages/opendoc-embed/README.md — the package's own usage, checked against the element
<script type="module">
  import "@casualoffice/opendoc-embed/define";
</script>

<opendoc-editor
  mode="readonly"
  editor-src="/opendoc/editor.html"
  frame-title="Contract preview"
></opendoc-editor>

It is mode and not role because role is a global ARIA attribute: role="readonly" would publish an invalid ARIA role to every assistive technology on the page. frame-title has no default — an iframe with no accessible name is an axe frame-title violation, and the package has no business inventing English for your page, so you get one console warning and no label.

Mounting from script is the same three attributes. This is the code the demo host in this repository runs, not a paraphrase of it — the embed demo page mounts the editor twice, once this way and once as a hand-wired iframe, and the browser suite drives both:

webapp/src/embed_host_demo.js — mountElement()
/** The custom element's own path: the host sets `mode` and nothing else, and
 *  the element resolves, sandboxes and reports. The readout is taken from the
 *  element's event rather than recomputed here — if the page and the element
 *  disagreed, the page would be hiding it. */
function mountElement(role) {
  const element = document.createElement("opendoc-editor");
  element.setAttribute("mode", role);
  element.setAttribute("editor-src", EDITOR_SRC);
  element.setAttribute("frame-title", panel.dataset.frameTitle ?? "");
  element.addEventListener("opendoc-capabilities", (event) => {
    render(panel, {
      capabilities: new Set(event.detail.capabilities),
      editingMode: event.detail.editingMode,
      sandbox: event.detail.sandbox,
    });
  });
  return element;
}

Setting mode or editor-src on a live element remounts it rather than retuning it. A permission handed over after the document is already on screen was never a permission.

You do not have to use the package. A host can wire the iframe itself — and this is what that costs, which is also the argument for the element: every line here is a decision the element already made.

webapp/src/embed_host_demo.js — mountIframe()
/** What a host writes with no package at all — and why they should not have
 *  to. Every line below is a decision the element already made: put the mode
 *  in the URL before the frame is attached, derive the sandbox from the
 *  capability set, and give the frame an accessible name. */
function mountIframe(role) {
  const url = new URL(EDITOR_SRC, document.baseURI);
  url.searchParams.set("mode", role);
  const resolved = resolveFor(role);
  const frame = document.createElement("iframe");
  frame.setAttribute("sandbox", resolved.sandbox.join(" "));
  frame.setAttribute("allow", "clipboard-read; clipboard-write");
  frame.title = panel.dataset.frameTitle ?? "";
  frame.src = url.href;
  return frame;
}

Resolution is pure and has no DOM, so a host can ask what a role grants before mounting anything — which matters, because each embed holds its own WebAssembly instance and a page should not have to boot one to find out what it would be allowed to do:

webapp/src/embed_host_demo.js — resolveFor()
/** The capability set, review mode and sandbox for a role, as an embed would
 *  see them: `framed: true`, because every embed on this page is framed. */
function resolveFor(role) {
  const capabilities = resolveCapabilities({ mode: role, framed: true });
  return {
    capabilities,
    editingMode: editingModeFor(capabilities),
    sandbox: sandboxTokensFor(capabilities),
  };
}

A host that wires its own iframe passes the same vocabulary in the URL: ?mode=readonly. Framing alone is enough — a page that is not the top window resolves to embedded without the host having to discover a parameter, which is the whole point: the defect this closed was a framed editor being a standalone one, with File ▸ Open live inside someone else's page. ?autosave=1 and ?autosave=0 move the one per-capability override there is.

Per capability, not per tier

The roles are names for subsets, never the unit of enforcement. Nothing downstream branches on a role name: the review mode, the sandbox tokens and every gated command are computed from the capability set. That is what makes "print, download, save, edit and comment are withheld independently" a property of the design rather than a promise.

Today's limit

The set is per capability, but the host's input is not yet: a host picks one of the 8 accepted names and may override autosave. There is no capability list a host can pass, so "commentor, but no printing" is not expressible today — it is a one-authority change rather than a new mechanism, and it is listed under what this does not do yet.

preview is not readonly

They are two different presentations, not two rungs of a ladder. preview is the runtime as a layout and rendering engine — a picture of the document, for a thumbnail, an attachment preview, a search result. readonly is a reading experience of a published document: navigation, outline, find, zoom, page controls and a paper copy. The test of the difference is whether a static image could replace it: for preview, nearly; for readonly, no, because the reader navigates and searches. So preview is not "readonly minus print".

What is true today

The capability sets already differ, and so does the frame's sandbox. The chrome does not: both roles land in the editor's Viewing mode with the full editing chrome present and its controls disabled, rather than a minimal canvas and a reading surface respectively. Composing a surface out — a readonly container with no editing ribbon at all — is designed and not built, and a wall of greyed controls is not the intended answer for these two roles.

Three layers of enforcement

In order of how hard they are to defeat.

1 · The browser. The element derives the iframe's sandbox tokens from the capability set, and the browser does not negotiate: a frame without allow-downloads cannot start a download however its chrome or its engine is persuaded, and one without allow-modals cannot open the print dialog. For comparison, ONLYOFFICE's createIframe (apps/api/documents/api.js:1279) sets no sandbox attribute at all — that file contains the string nowhere — so this is a layer they do not have.

2 · The engine. A capability set maps onto the editor's three existing review modes: edit → Editing, comment → Suggesting (every body change recorded as a tracked revision), neither → Viewing. Viewing is read-only at a single fail-closed choke point that refuses every mutation path — typing, deletion, paste, toolbar formatting, table operations, comment and revision decisions — rather than relying on any individual control being disabled. A readonly embed is therefore in Viewing on arrival, not an Editing page with dimmed buttons, and the browser suite proves it by stripping every disabled and aria-disabled attribute in the frame and then attacking the document with typing, paste and 17 ribbon commands, one by one rather than a sample. The evidence is the engine's own word and character counts, not the DOM.

3 · The chrome. A withheld capability disables its control with a reason and never hides it: a control that vanishes teaches nothing, and a product that silently lacks a feature is indistinguishable from one that is broken. Open the command palette inside a readonly embed and look at Open… — it is present, it is disabled, and its title says why. This is the layer that is least complete today: the editor page consults 5 of the 9 capabilities.

The other 4 are not consulted by the chrome at all. print, download and save are withheld by the sandbox — which works, but the refusal arrives from the browser rather than from a control that explains itself, and the editor's own status line can still report a save that the browser declined. branding is consulted nowhere yet: withholding it does not remove OpenDoc's mark from the frame. Both are listed below rather than left to be discovered.

Nothing here is gated

The package is Apache-2.0 and consults no licence, in any code path. That is the whole competitive position rather than a footnote: ONLYOFFICE's host-customization path early-returns when the editor is not licensed — apps/common/main/lib/controller/LayoutManager.js:68, if (!_licensed || !config) return; — so the customization a host is offered is a licence check away from doing nothing. Gating ours would surrender the only structural advantage that cannot be copied.

How this page is kept honest

The pages of this site have carried fabricated claims twice, in both directions — a parity figure that contradicted the fidelity page, a corpus file that did not exist, a repaint timing with no benchmark, and three shipped features listed as "Not yet". Understating is also false. So this page is built the way the package is:

webapp/tools/build-embed-docs.mjs generates every code panel, every table and every number above from the code they document, and --check fails when the committed page is not what a fresh run produces. That makes both directions of drift a build failure: editing the page by hand, and changing the code without regenerating the page. webapp/tests/embedding_page.test.mjs then re-derives the numbers independently of the generator, proves each extracted snippet still appears verbatim in the file its caption names, and proves every item under "does not do yet" is still true. Both run in the browser-smoke job of .github/workflows/ci.yml, which is itself asserted, because a gate nobody armed has been claimed here before.

What this does not do yet

Phase 1 is one of three. Each item here is checked by the guard, so it cannot outlive the gap it describes.

  • No command or event API. You cannot tell the embedded editor to do something, or be told what it did. The element fires exactly one event — opendoc-capabilities, once per mount, which is the capability contract announcing itself, not the editor reporting on a document. There is no postMessage protocol in the package at all. One schema over two transports (in-process and postMessage) is phase 2.
  • No way to hand it your document. The element takes mode, editor-src and frame-title, and nothing else. editor-src may carry the editor's own query parameters; there is no host-supplied document URL or byte array.
  • No host capability list. A host picks one of the 8 preset names and may override autosave. An arbitrary "these five, not those four" list is not accepted yet, so a configuration like "comments only, everything else off" cannot be expressed.
  • No reading or preview chrome. readonly and preview get the editing chrome with controls disabled, not a reading surface and a bare canvas. The two presentations are designed; the surface composition that would make them real is not built.
  • A browser-enforced refusal does not explain itself. Withholding print, download or save is enforced by the sandbox, and the control that triggers it is still offered — so the refusal arrives as the browser declining, and the editor can still report a save that never reached the visitor's disk.
  • Withholding branding does nothing. The capability exists and is refused to every role but owner, but no code consults it, so the editor still shows its own mark inside your page. White-labelling — name, mark, theme tokens, chrome selection and string overrides — is phase 3.
  • No framework bindings, by choice. A custom element needs no binding layer; the package ships none and declares no framework entry point. The repository exercises it in plain HTML and in Node, not inside a framework.
  • Not published. No workflow publishes the package to a registry. Install the tarball, or vendor the files.
  • No passwords. Deliberately out of scope until there is format work to make an encrypted document mean anything.

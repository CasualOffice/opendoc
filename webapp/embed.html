Embedding OpenDoc

The same editor, embedded twice on one page: once in a plain <iframe> a host wires itself, and once through the <opendoc-editor> custom element. Both resolve their capabilities from one authority before the frame's first navigation, so neither can be talked out of the mode it was given — and each panel prints the code a host writes to get it, which is the only real difference between them.

          What each layer actually enforces
          
          
          
            The browser refuses a download the sandbox did not allow. The engine
            refuses a mutation in Viewing mode at a single fail-closed choke point,
            so a chrome defeated from devtools still meets it. And the chrome
            disables a withheld capability with a reason rather than
            hiding it — a control that vanishes teaches nothing, and a product that
            silently lacks a feature is indistinguishable from one that is broken.
            Open the command palette inside a readonly embed and look
            at Open…: it is there, it is disabled, and it says why.
          
          
        
          
        
          
          
          And the fourth layer: the API
          
          
          
            A host that was not granted edit must not be able to run an
            editing command through the SDK either, or the API is simply
            the unlocked door beside three locked ones. So the capability gate runs
            before dispatch: pick preview above, mount, and
            run format.bold on either transport — the result is
            {"ok": false, "refusal": {"code": "capability-withheld"}}
            and the command never reaches the engine. Withhold
            download and run file.export.docx for the same
            answer. A refusal is a value, not just a toast.

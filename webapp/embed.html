Embedding OpenDoc

The same editor, embedded twice on one page: once in a plain <iframe> a host wires itself, and once through the <opendoc-editor> custom element. Both resolve their capabilities from one authority before the frame's first navigation, so neither can be talked out of the mode it was given.

Neither editor boots until you ask. Each one holds a WebAssembly instance of roughly 100 MB, and a page that starts two of them on load is a page that costs a visitor 200 MB for a demo they may not have wanted — the same reason the home page's live demo is click-to-activate.

      What each layer actually enforces

      The browser refuses a download the sandbox did not allow. The engine refuses a mutation in Viewing mode at a single fail-closed choke point, so a chrome defeated from devtools still meets it. And the chrome disables a withheld capability with a reason rather than hiding it — a control that vanishes teaches nothing, and a product that silently lacks a feature is indistinguishable from one that is broken. Open the command palette inside a readonly embed and look at Open…: it is there, it is disabled, and it says why.

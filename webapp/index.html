Open-source DOCX infrastructure

Own the document engine, not the dependency.

OpenDoc is a deterministic, embeddable Word-document runtime written in Rust. Import, edit, lay out, render, and write .docx across native, WebAssembly, and headless hosts—without a required server or UI framework.

Built for document systems

A runtime beneath your product—not another iframe around someone else’s.

OpenDoc keeps the normalized model and deterministic layout engine authoritative. The browser canvas is a rendering surface, never the document source of truth.

01

Loss-aware DOCX

Parse OOXML into a typed editable model. Safe unsupported package data is retained or surfaced explicitly instead of disappearing during save.

  • Semantic import and export
  • Byte-identical unedited reconstruction
  • Compatibility dispositions
02

Deterministic layout

Shape, paginate, compose, and rasterize from one Rust pipeline with pinned inputs and regression gates for geometry, collisions, and page output.

  • Paragraphs, tables, sections, floats
  • Backend-neutral display list
  • CPU fidelity oracle
03

Embeddable editing

Route public mutation through a closed command set with inverses, selection anchors, undo/redo, and host-owned network, storage, and authentication policy.

  • Native, web, and headless targets
  • No mandatory React or provider
  • Incremental browser repaint
A hard host boundary

Document semantics in Rust. Product policy in your hands.

The engine owns document state, transactions, selection, pagination, hit testing, and serialization. Your host owns files, fonts, network access, telemetry, permissions, and product UI.

Pre-release

Serious architecture. Honest support claims.

OpenDoc already imports, edits, lays out, renders, and writes real DOCX files, but it is not yet a stable SDK or a pixel-perfect replacement for Word. Fidelity is tracked with generated fixtures, LibreOffice comparisons, and CI gates rather than feature checkboxes.

Where the project is going

DOCX fidelity first. A broader document platform next.

The current priority is trustworthy DOCX compatibility. These are planned directions, not claims about today’s release.

Current focus

Deep DOCX fidelity

Close layout, pagination, round-trip, and interaction gaps against generated corpus evidence and established desktop renderers.

Future goal

Stable SDK release

Versioned Rust and WebAssembly APIs, self-hostable packages, and durable embedding contracts for production applications.

Future goal

More document formats

Extend the normalized runtime beyond DOCX to ODT, plain text, and additional document formats without forking the editing engine.

Future goal

Native PDF export

Produce PDF from the engine’s own deterministic layout and display list rather than routing documents through a browser print path.

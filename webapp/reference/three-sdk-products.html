Three SDK products on one engine: Viewer, Editor, Native

Owner decision, 2026-10-23. Split OpenDoc into three products on one engine, and market each one against named competitors:

  1. Viewer SDK. Read-only preview, in the browser (WASM + JS) and on a server. Competes with docx-preview and mammoth.js.
  2. Editor SDK. Today's <opendoc-editor>. Competes with ONLYOFFICE Docs.
  3. Native/headless SDK. Create, read, modify and convert documents in code, from Java, Python, .NET and C. Competes with Apache POI (XWPF), python-docx, docx4j, the Open XML SDK and Aspose.Words.

Owner scope clarification, same day, binding on the Viewer and Native SDKs. Both are API design only: no editing UX, no chrome, no UI work. Both are batch, request in and result out (open → read or modify → save, render or convert). Neither needs interactive re-layout or real-time re-render. Both must be light: they exclude the shell, selection, caret, hit-testing, the incremental-paint machinery and collaboration. The Editor SDK stays as it is and appears here only for contrast.

1. The finding that shapes the design

docs/83 §2 designed preview as a readOnly mode of the editor runtime: mutation entry points are bypassed at run time. That saves the reader nothing, because the bytes are already downloaded. The browser artefact is casual-doc-wasm, and every host gets all of it: 25,955,980 B, of which 12,044,435 B is code (§4.1). That code includes the caret, selection, hit-testing, the galley cache, the windowed body, the transaction log, diff and the collaboration client, whether the host edits or not.

So a product here is a dependency cut, not a run-time mode. The cut is measured below, and it removes 64% of the code.

2.1 What "deterministic pixels" means here

The viewer cut opens with only the bundled faces and the ones a host registers (ParleyShaper::without_system_fonts, crates/casual-doc-viewer/src/lib.rs ViewerOptions). The same bytes then lay out to the same pages and pixels on a laptop, a CI runner and a server. OS fallback (CJK, symbols from the machine) is an explicit ViewerOptions::with_system_fonts(true), and the host accepts that the pixels then depend on the machine. This is the browser's configuration already. It was made the default here after a measured failure (§9 R3).

3.3 Native/headless SDK

One Rust API, projected through one C ABI (§6), with idiomatic thin wrappers per language. It covers four call families. All of them are batch calls.

Deliberately absent from the Native SDK: selection, caret, viewport, input, events, undo and redo stacks, collaboration and diff. edit returns the inverse batch, so a host that wants undo has it without a history object.

Why edits go through Operation, not a writable DOM. A DOM of mutable model structs would make every model field a public API. It would also bypass ADR-030 I1, the single mutation choke point, and with it the invariants the operation set enforces: ids, section and list integrity, review marks and protection. POI's own page warns of the cost of a writable low-level surface: "Error checking may be missing in places, so it may be possible to accidentally generate invalid files" ([POI document page][poi]). The read view is a projection, and every write is a typed operation.

Rules:

  1. Features add, never subtract. default = [] is the smallest useful thing (DOCX → pixels). A feature that removed capability would make --all-features, which CI lints, the smallest build, which is backwards.
  2. One engine version. Every crate and package carries the workspace version, so a Viewer page and an Editor page render one document identically when both are on x.y.z.
  3. The editor is never a consumer of the viewer crate. If it were, a viewer refactor could move editor bytes. The two share the engine crates below them, not each other.

5.3 Versioning

SemVer, 0.y until the owner declares an API stable, and docs/05 §12's policy from 1.0. There are three version numbers, and each one is independent:

  • the engine/package version, one for every product;
  • the C ABI version (opendoc_abi_version()), bumped only when a symbol's signature or ownership rule changes, so a Java jar can refuse a mismatched native;
  • the schema versions (normalized JSON, docs/05 §12).

6. Binding strategy: recommendation

Recommended: one handle-based C ABI (casual-doc-ffi) as the single contract, with a generated header, and thin hand-written idiomatic wrappers per language.

Option For Against
C ABI + generated header (cbindgen), wrappers per language One unsafe surface, one ownership rule (opaque handles, opendoc_free_*, error as code plus message). It serves C/C++, which docs/05 §1 promises, and every runtime can call C: Java FFM, .NET LibraryImport, Python ctypes/cffi The wrappers are hand-written. Mitigation: a conformance suite run through every language against the same fixtures
PyO3 (Python), JNI (Java), a .NET-specific binding Most idiomatic per language Three bindings written against Rust directly, three unsafe surfaces, three release pipelines, and still no C
UniFFI Generated idiomatic bindings Officially "Kotlin, Swift and Python" ([UniFFI][uniffi]). Java and C# are third-party generators ([UniFFI README][uniffi-readme]: IronCoreLabs/uniffi-bindgen-java, NordSecurity/uniffi-bindgen-cs). There is no C output
WASM everywhere (Wasmtime/Chicory hosts) One artefact A WASM runtime dependency in every JVM/.NET host, and slower than native. Unmeasured, so not recommended without a measurement

Java: the Foreign Function & Memory API was finalized in JDK 22, and its JEP's goal is to "Replace the brittle machinery of native methods and the Java Native Interface" ([JEP 454][jep454]). Java 8–21 users would need a JNI shim over the same C ABI. Whether to carry that shim is Q3.

The unsafe exception. The workspace sets unsafe_code = "forbid". A C ABI needs #[unsafe(no_mangle)] and raw pointers, so casual-doc-ffi must be the one crate with a recorded exception (a crate-level [lints] override), fuzzed at the boundary, and nothing else may relax the rule (P4).

8.3 Releasing to npm (pre-releases)

.github/workflows/npm-publish.yml publishes @casualoffice/opendoc-viewer (packages/opendoc-viewer) and @casualoffice/opendoc-editor (packages/opendoc-embed). It runs only when dispatched by hand, and only ever publishes a pre-release under the npm next tag; latest is never touched, so npm install <name> without a version does not resolve to a pre-release. webapp/tests/npm_publish_workflow.test.mjs asserts each of those properties.

Inputs: package (viewer, editor or both), version (semver with a pre-release part, for example 0.1.0-alpha.1; 0.1.0 is refused) and dry_run (default true).

What a run does, per package: build (the viewer through packages/opendoc-viewer/build.sh, Rust from rust-toolchain.toml, wasm-pack 0.15.0), run the package's own tests, set the version with npm version --no-git-tag-version in the runner's checkout (the editor also regenerates src/release.mjs, which reports the installed version), npm pack --dry-run, then npm publish --tag next --access public --provenance, with --dry-run when dry_run is true. The version is never committed: the tree stays at 0.1.0.

Auth: npm trusted publishing (OIDC) with npm 11.6.2, through the github-pages environment, which holds the npm credentials. If that environment's secret NPM_PASSWORD is set (an npm access token), only the publish steps receive it as NODE_AUTH_TOKEN. A package's first publish needs that token, because npm lets a trusted publisher be configured only on a package that exists; after it, add the trusted publisher on npmjs.com (repository CasualOffice/opendoc, workflow npm-publish.yml, environment github-pages) and the token can be removed. A real publish runs from main only.

Steps:

  1. Dry run from main, and read the npm pack --dry-run file list in the log: gh workflow run npm-publish.yml --ref main -f package=both -f version=0.1.0-alpha.1 -f dry_run=true
  2. Publish: the same command with -f dry_run=false.
  3. Check: npm view @casualoffice/opendoc-viewer dist-tags shows the version under next and no latest. A version number can never be reused, even after an unpublish, so the next attempt takes the next pre-release number (0.1.0-alpha.2).

  2. A loss report on every open and every save (import_report, SaveReport.losses) and three save modes: exact returns the original bytes when the document is unchanged, preserve keeps verbatim-retained parts, semantic regenerates. No library in §12.1 reports loss.
  3. Templating in the same package, with images, tables, footnotes and headers kept because the engine edits the document rather than the XML text. docxtemplater charges for several of these as modules.
  4. Every edit goes through the engine's checked operation set (ADR-030 I1): ids, protection (a read-only document refuses), atomic batches and an exact undo. POI warns it "may be possible to accidentally generate invalid files"; here a batch either applies whole or not at all.

  • docx-js's silent skip of an unknown option. Here an unknown spec field is an error naming the field, except inside TextRun and Paragraph, whose options flatten into one object.
  • docxtemplater's default nullGetter, which prints undefined. Here a missing value prints "", or is an undefined_value error with strict.
  • python-docx's writable proxies over the XML. Here a run's bold = True is a typed edit.

Offsets. Edits address text by character (Unicode scalar) offsets into a paragraph's text, which is a Python str index. JavaScript UTF-16 indices differ only outside the BMP, and the JS package converts.

12.3 The Rust core (S1), as built

crates/opendoc is the one public façade (docs/176 §5.2). It re-exports no casual-doc-* type.

  • Open and create. Document::open / open_with(bytes, OpenOptions) go through the casual-doc-io registry: DOCX, ODT, RTF, TXT and JSON, plus PDF with the pdf-import feature. The source is retained, so an exact save works. Document::create() and from_spec(DocumentSpec, media) build a WordprocessingML package and open it. It carries Word's built-in style ids and names (Normal, Title, Heading 1-6, List Bullet, List Number, Quote, Caption, Table Grid, Hyperlink, the TOC and note styles), an A4 page and Calibri 11 pt, which the bundled Carlito lays out metric-identically.
  • Read view (opendoc::view): body() returns Block::{Paragraph, Table, ContentControl, Other} with stable ids. Paragraphs carry their style name, text, heading level, alignment, list membership and runs. Runs carry text, direct formatting, hyperlink, tracked change, field, image and note/comment references. Also paragraphs(), tables(), sections(), styles(), comments() (with anchors), revisions(), headers_footers(), notes(), media() plus media_bytes(), properties() and text(). Everything serialises to the camelCase JSON every binding reads.
  • Edit (doc.edit(|e| …), or edit_commands(&[EditCommand]) from JSON). The text, format, hyperlink and paragraph calls lower to casual_doc_edit::Operation and apply through casual_doc_edit::apply after refuse_if_protected. They are: insert_text, delete_text, replace_text, replace_all, set_run_format, clear_formatting, set_hyperlink, set_paragraph_style, set_alignment, set_page_break_before, insert_paragraph, append_paragraph, append_heading, append_run, delete_block. Tables: insert_table, set_cell_text, add_row, delete_row. Review edits lower through casual_doc_review::lower, the editor's own lowering: add_comment, suggest_insert, suggest_delete, suggest_replace, accept_all_revisions, reject_all_revisions. Properties: set_properties. The batch runs on a copy and replaces the document only if every call succeeded. It returns an exact Undo, which doc.undo applies and which returns the redo.
  • Template: render_template(data, TemplateOptions) and template_tags(), the docxtemplater idiom of §12.2 lowered to InsertText, DeleteText, InsertBlocks, DeleteBlocks, InsertRow, DeleteRow and SetInlines.
  • Save: save(Format, SaveMode) -> (bytes, SaveReport) to DOCX, DOTX, ODT, TXT, JSON, HTML, Markdown or PDF. A same-format save honours the mode. A cross-format save is semantic and its report says lossyByNature for the renditions. opendoc::convert(bytes, to) does both steps in one call.
  • Render: page_count, page_sizes, page_text, render_page (RGBA), render_page_png, to_pdf, outline and font_needs. One layout serves all of them, cached until the next edit. It uses bundled faces by default (RenderOptions adds faces or allows OS fonts).
  • Not built (stated, not hidden):
    • inserting pictures, headers, footers or notes by edit (the builder writes all four);
    • page or section edits;
    • paragraph loops inside headers and footers (value tags work there);
    • SVG (no backend, §3.1);
    • opening HTML or Markdown (export-only adapters).

One defect class found and handled in the SDK. A comment's anchor from casual_doc_review is measured in the layout anchor stream, which counts a footnote reference's printed number. The read view's text does not count it, so the first build returned "noted " for a comment on " noted" after a footnote. Document::comments and revisions now map anchors through both length functions (ParagraphSpace). The engine-side disagreement is the one recorded on casual_doc_review::body::inline_anchor_len.

An engine limit the builder found, now fixed in the importer. A complex field whose begin and end sit in one paragraph, with a hyperlink in its cached result, failed the whole DOCX open: model validation refuses a hyperlink inside a Field's inlines (a field's result is leaf-only), and the importer turned that into "a fault in the document engine". A one-entry linked table of contents written that way is a valid file. The builder writes Word's own shape, a field range (a_linked_table_of_contents_opens_and_lists_each_heading). casual-doc-import now degrades such a field to its result (commit_field, segments_are_field_leaves): the entry, its hyperlink and its text are kept, and the dropped instruction is reported as fldChar or fldSimple. Guard: a_single_paragraph_field_around_a_hyperlink_degrades_to_its_result, for both encodings. Mutation: with the leaf check forced true, the open failed again with Model(NestedHyperlink(..)).

12.6 The CLI (S3): opendoc, also the server preview engine

tools/opendoc-cli builds one binary, opendoc, over crates/opendoc with PDF import on:

text

  • Exit codes. 0 is success. 1 is a document or engine error, and the message starts with its stable code (open:, template:, …). 2 is a usage error. 3 means convert --strict-loss refused a save that would lose content.

12.6a The core's edit cost

A batch used to run on a copy of the whole model, so it could be all or nothing. That makes a python-docx-style loop quadratic, because each add_paragraph is one batch and copied the document. Document::edit now applies to the live model and, on a refusal, rolls back through the inverses casual_doc_edit::apply returned. That is the engine's own exact undo, so a batch costs O(the batch) and not O(document). Document::paragraph(id) and table(id) project one node, so a binding does not re-project the body per call.

  • Guard. a_failed_batch_leaves_the_document_unchanged compares the whole model's JSON snapshot before and after a refused batch that had replaced text and inserted a table.
  • Mutation. With the rollback skipped, that test went red: the text still read THE.

12.9 The C ABI and Java (S5)

crates/opendoc-ffi is the §6 recommendation, built. It is one handle-based C ABI with version 1 (opendoc_abi_version) and a header, include/opendoc.h.

  • Ownership rule. Every OdDocument * and OdBuffer * belongs to the caller, who frees it once. Inputs are borrowed for the call and copied.
  • Errors. A failure returns NULL and records a thread-local message that starts with the stable code. A panic is caught at the boundary and becomes an engine error.
  • Surface.
    • Bytes: opendoc_open, opendoc_create, opendoc_from_spec, opendoc_save, opendoc_render_png, opendoc_to_pdf, opendoc_compare, opendoc_convert.
    • opendoc_call: every read and edit by method name with a JSON argument, which is the JSON the other bindings read.
    • Buffer access and free.
  • The recorded unsafe exception (P4, R5). This is the only crate whose [lints] are not workspace = true. It copies every workspace lint except unsafe_code. Each unsafe block is a boundary read with a SAFETY comment.
  • Not built. The header is hand-written, because cbindgen is not installed here. the_header_declares_every_export fails if an export is missing from it. The boundary is not fuzzed yet (P4).

bindings/java uses the Foreign Function & Memory API (JEP 454, final in JDK 22) over that ABI, with no JNI glue and no dependency. Json.java is a 200-line reader and writer. The naming is POI XWPF's:

  • OpenDocument (XWPFDocument): new OpenDocument(), new OpenDocument(InputStream), createParagraph, createTable(rows, cols), getParagraphs, getTables, getText, write(OutputStream).
  • OpenParagraph: createRun, setStyle, setAlignment(ParagraphAlignment), getRuns.
  • OpenRun: setText, setBold, setItalic, setUnderline, setStrike, setFontSize, setFontFamily, setColor. Formatting can be set before the text, as in POI.
  • OpenTable: getRow(i).getCell(j).setText, createRow.

Aspose's save(path) takes the format from the extension, and its getPageCount and replace are kept. The binding adds toPdf, renderPagePng, renderTemplate, acceptAllRevisions, compare, getImportReport and getLastSaveReport. It is built locally only (bindings/java/build.sh), against JDK 22 or later; JDK 8-21 would need the JNI shim of Q3, which is not built. Nothing goes to Maven Central.

  • Guards.
    • crates/opendoc-ffi/tests/abi.rs (4 tests) calls the ABI through raw pointers: open/read/edit/save/render/free, NULL and coded errors (a null pointer with a length is refused), convert and compare, and the header check.
    • bindings/java/.../ConformanceTest.java makes 21 checks run by build.sh.
  • Mutation. Formatting set before the text not applied: ConformanceTest failed at "format set before the text lands on it" (NoSuchElementException, because the 12% run never split out).

The suite measures time, peak memory, page counts, and round-trip survival (package parts kept, body text unchanged, OpenDoc's own loss report). It writes benchmarks/sdk/results.json. The table below is rendered from that file by benchmarks/sdk/report.mjs, and packages/opendoc/test/bench_record.test.mjs fails if the two disagree. To run it: node benchmarks/sdk/run.mjs --deps DIR [--python PY] [--soffice PATH], on an idle machine. DIR holds an npm install of docx, mammoth, docxtemplater and pizzip. Nothing from it is committed.

Read it honestly. The table makes six points.

  • In JavaScript, OpenDoc is faster than mammoth at HTML and text, and level with or faster than docx-js at generation. It is slower than docxtemplater at filling a template.
  • In JavaScript it uses more memory in most tasks, because the module carries a layout engine and every bundled face. Its floor is the module itself, and docx-js passes it on the largest input. The Python and Java bindings link the same engine natively and use less memory than python-docx and POI in most rows.
  • Python generation is several times faster than python-docx, at every size measured. Reading is level with or faster than python-docx.
  • Java generation is faster than POI on a small document and slower at 1,000 paragraphs. Reading is faster than POI on the smaller file and level on the large one.
  • A defect the first run found, fixed for the class. The first full run (2026-10-30) had Java generation 7.1× slower than POI at 1,000 paragraphs and Python losing to python-docx at 5,000, with the gap growing with the document. Measured in the Rust core, a paragraph step was constant (3.5 µs at 1,000 and at 4,000 paragraphs), so the cost was in the bindings, for two reasons:
    • every table access went to the paragraph locator first, and a table id is a cold miss there that walks the document;
    • every getRow, getCell, cells and cell(r, c) re-projected the whole table to check bounds, which is O(rows) per cell and O(rows²) per table.

Both bindings now look tables up as tables and keep the table's shape, which createRow and add_row update. The core's step cost is guarded by a_builder_step_costs_the_same_on_a_document_twice_as_long (n against 2n, SKILL §8). The two costs that were left, both engine-side, are now O(1) in document size (2026-10-31), by the route-cache pattern casual_doc_model::v1::locate already used for paragraphs (memoization validated on use, docs/109 HF-184):

  • A table by id. Document::table/table_mut keep a direct-mapped cache of table routes, validated on every use. casual_doc_edit::find_table and the six row, column and table-property operations that walked twice (blocks_owning_mut, then find_table_mut) use it.
  • The first edit to a block just inserted. InsertBlocks into the body records the route of each block it placed (Document::hint_body_block), and the SDK's set_cell_text reaches the cell's paragraph through its table's route (Document::hint_cell_paragraph). A stale hint is a miss, never a wrong answer.

Guard: a_new_paragraphs_first_edit_and_a_table_lookup_cost_the_same_at_n_and_2n puts a table after n and 2n paragraphs and compares the engine's block-visit meter for a new paragraph's first run, and for two set_cell_text calls and an add_row. Its control, a lookup of an id that is not a table, must double, so equal numbers cannot come from a meter that counts nothing. Mutations, each red: the insert's hint removed (512 visits at n, 1,012 at 2n); the table hint disabled (4,039 against 8,039); the cell-paragraph hint removed (1,021 against 2,021).

  • docx-preview needs a DOM, so it is not measured here. docx4j is not measured. LibreOffice is in the suite (--soffice), but the copy on the measuring machine is a broken install, so its column is empty. The round-trip table shows python-docx keeping every package part, because it rewrites the zip it was given. OpenDoc keeps the text in every fixture and reports what its writer regenerates.

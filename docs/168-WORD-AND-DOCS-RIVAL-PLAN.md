# 168 — The plan to rival Word and Google Docs

**Status:** active, 2026-10-09. The tracker is `docs/109`: each batch below is one row there
(RM-17 to RM-45, and four existing Hotfix rows for batch 2). This document holds the order,
the scoring and the way each batch is run; `109` holds the state.

The owner's instruction, 2026-10-09: *"lets start by creating a detail tracker and anlaysis
and filling those gaps .. to make it rival of microsoft words as well as google docs … first
plaining and list and than targetig one at a time.. we need above 85 on all stages … combining
4-5 close task … and testing 4-5 task at once .. so .. less time no. of CI will be run"*.

So the plan has three parts:

1. A target that can be measured.
2. Every open gap assigned to exactly one batch.
3. A way of working that runs CI once per batch rather than once per fix.

## The target

There are five measures. The plan is done when every one of them reads 85 or more.

- **Read, Drawn, Editable and Saved** are the four stages of the public fidelity matrix
  (`webapp/src/fidelity.js`, shown on `fidelity.html`). Each construct family a DOCX can
  carry (tables, lists, fields, charts, …) is graded on each stage:
  - full = 1;
  - partial = ½;
  - kept unchanged or shown as a placeholder = ¼;
  - none = 0.

  A stage's score is the mean over the families.
- **Editing parity** comes from the capability matrix (`docs/153`). That matrix grades 422
  things a document user does against ONLYOFFICE's shipped editor, with a citation on both
  sides. The score counts a Partial as half: (Parity + Partial ÷ 2) ÷ (Parity + Partial + Gap).
  Rows that only we ship, and rows ONLYOFFICE gates behind a licence or its desktop shell, are
  outside the denominator, as the matrix's own tally keeps them.

### What the five numbers do not measure

- **The fidelity matrix is per family, not per document.** A family graded partial because
  of one rare construct costs as much as one partial because of a common one. The note on
  each row says which it is; the score does not.
- **The parity matrix compares against ONLYOFFICE.** It does not compare against Word or
  Google Docs. ONLYOFFICE's surface is close to Word's, but both rivals ship things
  ONLYOFFICE does not. They are listed under
  [What Word and Google Docs have that the matrix does not list](#what-word-and-google-docs-have-that-the-matrix-does-not-list).
  Adding them changes the denominator, so that is an owner decision, not a quiet edit.
- **A closed row is a claim until the evidence lands.** The projection assumes each batch
  closes what it names. A batch whose capability stays Partial says so in `docs/153`, and
  the projection moves with it, because both blocks are generated from the files.

## How the work runs

One batch is four or five related tasks. The tasks in a batch share crates and a surface,
so they share one build, one review context and one CI run.

### Each batch, in order

1. **Start from `main`, on one branch.** The batch's `109` row moves to `In progress`.
2. **Re-measure before building.** Read the docs/153 rows and the `109` rows the batch
   names, and confirm each is still open in the code. A row found already closed is
   re-graded with its evidence, not rebuilt. Understating is also false (SKILL §9).
3. **Build task by task, with the cheapest guard that proves the behaviour:**
   - engine behaviour gets a Rust test in the crate that owns it;
   - a pure webapp module gets a `node --test` unit test;
   - **only behaviour that exists solely in the browser** (a gesture, focus, a painted
     result, a dialog's wiring) gets a Playwright test. Each batch has one spec file of its
     own, which holds the browser tests for all of its tasks.
4. **While building, run only what the task touches:**
   - `cargo test -p <crate> <filter>`;
   - the one `node --test` file;
   - the batch's own spec.

   There is no workspace sweep and no full Playwright run per task.
5. **Drive every guard red (SKILL §4).** Reintroduce the defect, see the guard fail, and
   record the mutation and its red output in the commit message.
6. **Run the gates once, at the end of the batch, each on its own exit status:**
   - `fmt` and `clippy -D warnings`;
   - `cargo doc` with `-D warnings`;
   - `cargo test --workspace --all-features --locked --no-fail-fast`;
   - the wasm32 check;
   - the glossary, `build.sh` and `npm run test:unit`;
   - the batch's spec, plus every existing spec that drives a module the batch changed.
7. **Run the full Playwright suite locally only when the batch changes shared chrome:**
   `main.js`, the layout of `editor.html`, `style.css`, or the keymap. Otherwise CI's four
   shards are the verdict.
8. **Push once, open one PR, and drive it to green.**
   - Close the batch's `109` rows.
   - Re-grade the `fidelity.js` cells and `docs/153` rows the batch moved, each with its
     evidence.
   - Regenerate this document's blocks with `node webapp/tools/build-rival-plan.mjs`.

### Other rules

- **Copy-only and locale-only changes need no new test.** The locale coverage and string
  tests already hold them.
- **A documentation-only change runs the tracker tests and this plan's test,** not the
  workspace.
- **At most two batches run at once,** as agent lanes on disjoint crates and files, each
  with its own PR.
  - Each lane mints its `109` ids from a range the coordinator gives it, so two PRs never
    take the same id.
  - Disk is the binding limit: `CARGO_INCREMENTAL=0`, and clear `target/` between batches.
- **A batch that cannot finish a task says so in its PR.** The task's row stays open with
  the reason, rather than the batch shrinking in silence.

## The projection

The scores after each batch, if each closes what it names. The order runs in four phases:

1. Batches 1 to 6: the plan itself, the P1 correctness rows, and the formatting and typing
   work that moves Read and editing parity most cheaply.
2. Batches 7 to 16: the everyday editing surfaces, from page setup to review. These carry
   most of the editing-parity gaps.
3. Batches 17 to 24: protection, fields, forms, charts and the rendering and editing of
   complex objects. These move Drawn and Editable.
4. Batches 25 to 30: breadth past the target, namely table positioning, compare, proofing,
   view, print and export formats, and collaboration.

## The batches

Each heading names the batch's tracker rows. In each batch:

- **Moves:** the fidelity cells the batch raises, written `` `Family` stage → grade ``;
- **Closes in docs/153:** the capability ids the batch brings to Parity.

The test `webapp/tests/rival_plan.test.mjs` fails if any of the following holds:

- a capability that is open in `docs/153` is assigned to no batch, or to two;
- an id names nothing;
- a tracker row is missing from `docs/109`;
- a family is not in `fidelity.js`;
- the final row of the projection is under the target.

## What Word and Google Docs have that the matrix does not list

These capabilities are absent from `docs/153`, which compares against ONLYOFFICE. None of them
is graded or scheduled yet. Adding one to the matrix lowers editing parity until it ships, so
which ones to add is the owner's call.

- **From Word:**
  - citations and a bibliography;
  - an index (`XE` and `INDEX` fields);
  - a thesaurus;
  - Quick Parts, building blocks and AutoText;
  - Inspect Document (remove personal information);
  - Mark as Final;
  - sensitivity labels (Microsoft Purview) applied from the editor;
  - Read Aloud, Dictate and Translate;
  - Focus mode and Immersive Reader.
- **From Google Docs:**
  - pageless mode;
  - smart chips (people, dates, files, drop-downs);
  - document tabs;
  - emoji reactions on comments;
  - assigning a comment to a person;
  - link previews;
  - voice typing.

## Owner decisions this plan waits on

| Batch | Decision |
| --- | --- |
| 17 (RM-32) | Whether the editor may SET a Word password. ADR-052 records that a Word password is a policy marker, not security. Setting one means computing Word's legacy verifier here, and the dialog then has to say what that password does not protect. |
| 21 (RM-36) | Hyphenation dictionaries: which languages ship, and under which licences. The TeX pattern files are under several licences, and some are not compatible with Apache-2.0. |
| 24 (RM-39) | Equation editing: a structured palette, Word's linear format (UnicodeMath), or both. |
| 20 (RM-35) | Charts: which families past the six drawn today are worth drawing (3-D, stock, radar, bubble, the `cx` chartex families), against keeping them and showing a placeholder. |
| 30 (RM-45) | Collaboration: whether sharing needs a relay this project runs. Local-first is the stated position (`docs/149`). |
| — | Whether the Word and Google Docs list above joins `docs/153`, which would change the editing-parity denominator. |

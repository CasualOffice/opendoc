# 160 — Import loss, measured: what a real corpus actually loses, on both axes

**Status:** Measurement, with two fixes landed and a ranked queue behind them. 2026-10-04.
**Opened:** 2026-10-04.
**Scope:** DOCX import loss in `crates/casual-doc-import`, judged by the compatibility
report (`35-DISPOSITION-TAXONOMY.md`) and by a source-versus-written diff of the
**attribute** axis. Export is read but not changed. Nothing in `crates/casual-doc-layout`
or `crates/casual-doc-render`.

**Evidence base:** twenty `.docx` files the owner supplied privately, nineteen of which
import (one is a truncated download that `unzip` also refuses, so `MalformedArchive` is the
correct verdict and not a false rejection). **The corpus is confidential: no file, and
nothing derived from one, is committed, and nothing below names a document or quotes its
content.** Findings are construct names and counts only.

**Every number in this document is regenerated by a committed artifact** (skill §9 rule 1),
not maintained by hand. Run, pointing at a folder of `.docx`:

```sh
cargo run --release --example corpus_report -- <dir>            # the element axis
cargo run --release --example corpus_attribute_axis -- <dir>    # the attribute axis
```

The figures here are from the run of 2026-10-04 over nineteen importable documents. They
will move as the corpus and the writer move; re-run before quoting one.

## 1. Why this needed measuring rather than reasoning about

The product position is that direct OOXML with verbatim retention beats a
`DOCX -> Editor.bin -> DOCX` converter — but skill §1 states the condition plainly: that
advantage "is only real if loss is detected and reported". Nothing in this repository could
say which construct was lost, in how many documents. The two harnesses above are that
instrument, and they rank by **document frequency** rather than occurrence count, because a
construct missing in ten documents is one fix and a single exotic construct is not where to
start.

## 2. The element axis, and the thing that made it unreadable

Before any fix, the nineteen documents produced **15,680 findings across 98 distinct
features**. The top of the table by document frequency was almost entirely plumbing —
`a:theme/@name` and `a:fontScheme/@name` in seventeen documents, `a:objectDefaults` in
fourteen, the `w:rsid*` class in thirteen, `a:extraClrSchemeLst` in thirteen,
`w:themeFontLang` in twelve — all of it already known and already reported.

The interesting fact was in the occurrence column, not the frequency one. Two documents
contributed 1,833 `w:ind` and 1,689 `w:spacing` findings, and **every one of them was
false**: counted in the source, 1,837 of those `w:ind` elements and 1,688 of those
`w:spacing` elements carry **no attributes at all**. `<w:ind/>` specifies no indentation.
Nothing was lost, and the report said something was. The dominant location is
`w:style/w:tblStylePr/w:pPr` — a table style's conditional-formatting regions — which is how
two files produce thousands of findings each.

`apply_paragraph_property` decided "did I map anything?" by comparing the parsed value
against `Default::default()`, which cannot separate `<w:ind/>` (nothing specified) from
`<w:ind w:leftChars="720"/>` (character-unit indentation this parser does not read). Both
reached `return false`, so both were reported.

**Fixed**, with the distinction stated once as `carries_no_attributes`: **15,680 findings
to 12,159**. 22.5% of everything the report said about this corpus was this one false
class. That matters more than its size — `35` requires an ordinary document to produce an
empty report, because a report that fires on healthy files is one every caller learns to
filter out, and a filtered report cannot carry loss detection at all. At 22.5% noise the
report could not be used to rank anything, which is why it was fixed before anything else.
It is the same family as HF-174's no-op class work, one axis over: that lane silenced
elements whose *name* settles the question, this one the elements where only the attribute
list does.

## 3. The attribute axis, which no gate can see

`casual-doc-export/tests/source_element_coverage.rs` asks whether an element **name** in
the source vanished without a finding. Its own module doc records the limit: *"Attribute
names are a separate axis"* — and that axis is **not gated**. So an attribute can vanish on
import with a compatibility report of zero entries, which is exactly what happened to
`w:wrap@wrapText` (#739). *(Superseded since this measurement: the axis is gated by
`casual-doc-import/tests/attribute_loss_coverage.rs`, `109` HF-243, and the coverage gate's
module doc says so, `109` HF-268.)*

### 3.1 The reporting surface, enumerated

The importer can name an attribute through exactly **one** method, `Reporter::
report_attribute`, with **8 production call sites** covering roughly **22**
element/attribute pairs: `{p,r,tr,sectPr}/@{paraId,textId}`,
`{wrapSquare,wrapTight,wrapThrough}/@wrapText`, `anchor/@{distT,distB,distL,distR}`,
`sig/@{usb0..csb1}`, `{altName,panose1,charset,family,pitch}/@val`,
`{theme,fontScheme}/@name`, `lvl/@{tplc,tentative}` and `numFmt/@format`. Every site is a
hand-written literal; none is generic. `report_identity_attributes` early-returns unless
the element is `w:p`, `w:r`, `w:tr` or `w:sectPr`, and considers two attribute names within
those. `properties.rs`, `tables.rs` and `vml.rs` — the three parsers with the largest
attribute surface — have **no reporter in scope at all**.

The reason is structural, and worth naming because it decides what a fix can look like.
Attribute lookup is **pull-based**: `attribute_value(element, b"name")` asks for one literal
name. An attribute nobody asks for is therefore not merely unmapped, it is **unobservable** —
there is no code path on which its existence is visible, so no report site is possible at
the point of loss. Closing a silent attribute loss always means adding a question, never
just adding a report.

### 3.2 What the corpus actually loses silently

The harness diffs `(element, attribute)` pairs between source and written package, removes
the three subsumptions the element gate already applies, and removes two kinds of
non-loss: namespace declarations and `mc:Ignorable` (plumbing — a prefix is a property of
the producer, not of the construct), and attributes whose value says nothing (`""`, `"0"`,
`"false"`, `"off"`, `"none"`), which a writer legitimately expresses by omitting them.

**That second reduction is what separates measurement from noise**, and it is why `35`
was right to decline a bare-name attribute gate in 2026-09. Without it the table is headed
by `w:tblLook@w:lastRow` (seven documents) and `w:tab@w:leader` (three) — and checked by
value, both are spelling: `w:tblLook@w:lastRow` is `"0"` in eight documents and `"1"` in
one, the writer emits only the true flags, and the explicit off correctly vanishes;
`w:tab@w:leader="dot"` occurs in three documents and **survives** the round trip, while the
`"none"` in four does not need to. Reading values drops 14 of 85 pairs, including both of
those headline rows.

**71 pairs survive all five reductions.** Ranked by documents, with spelling identified as

## 4. The one that was fixed: border theme colour

Five of nineteen documents lose a border theme colour. The slots are real
(`accent1`-`accent5`, `text1`, `background1`) with real tint bytes, on six edge names, in
both `word/document.xml` and `word/styles.xml`.

`BorderEdge::color` is `Option<RgbColor>`, and the model's own doc comment on that field
says "explicit sRGB only; `auto`/theme reported". **The second half was not true.** Both
edge builders — `styles.rs::border_edge` and `body.rs::build_border_edge`; the builder
exists twice — read `@w:val`, `@w:sz`, `@w:color`, `@w:space` and let the theme triple fall
off the end with no reporter in reach.

This was first closed by *reporting* it: one shared `report_border_theme_color` wired into
both builders emitted a `Degraded` attribute finding per attribute. Reported rather than
modelled deliberately, because widening `BorderEdge::color` to the `Color` type runs
already use would change a widely-constructed model struct, and honouring a theme colour
on the page needs a consumer in `casual-doc-layout` — both of which that lane named as
follow-on work rather than implying them.

**That follow-on work has since landed, and the report is gone with it.** `docs/161`
models the triple in `BorderEdge::theme_color` beside the sRGB fallback Word writes next to
it, collapses the two edge builders into one shared `properties::parse_border_edge` — the
duplication is why the triple had to be dropped twice to be dropped at all — and gives
`casual-doc-layout` the consumer that paints the resolved slot. Once the value survives,
reporting it `Degraded` is a false finding of exactly the class this measurement existed to
remove, so `report_border_theme_color` was deleted. The guard that holds the line,
`a_border_theme_color_survives_the_import_or_is_reported`, is deliberately written at the
altitude of *survives or is reported*, which is why it stayed green across both halves
instead of reddening on the fix.

## 5. Three recorded gaps, verified

- **`w:vanish` (hidden text) — REFUTED on its central claim.** The draw-time check exists:
  `casual-doc-layout/src/flow.rs` returns early from `push_styled_runs` when the cascaded
  `hidden` is `Some(true)`, and three tests pin it. Hidden text does not render. What *is*
  true: there is no "show hidden text" toggle and no editing operation that applies or
  clears `w:vanish` anywhere in `webapp/`, `packages/` or `crates/casual-doc-wasm`;
  `w:specVanish` is carried through the cascade and consumed by nothing; and the two
  recomputed field kinds (`PAGE`, `NUMPAGES`) build their item without consulting `hidden`,
  so a hidden page number would still paint. Those three are the residual, and they are
  authoring and UI work, not import work.
- **Password-protected round-trips to password-less — CONFIRMED, and measured at one
  document of nineteen.** Import reads `w:documentProtection@w:edit`, `@w:enforcement`,
  `@w:formatting` and `w:writeProtection@w:recommended`, and silently discards the whole
  `AG_Password` group. Nothing *was* reported, because a finding is raised only when
  `apply_setting` returns `false` and these return `true` — fixed since: the parser now
  reports every password attribute on either protection element by name (§7 item 5).
  `word/settings.xml` is a
  *consumed* part, so the opaque side-table does not byte-preserve it either: the loss is
  semantic-mode-only, and `Retention` mode still keeps the original bytes. The protection
  therefore survives as a restriction that lifts in Word **with no password**. Already
  described in `08-ADR-REGISTER.md` and in `153-ONLYOFFICE-CAPABILITY-PARITY-MATRIX.md`;
  what is new here is that it is silent as well as unmodelled, and that the corpus confirms
  it is reachable rather than theoretical.
- **VML `v:wrap@side` not parsed — CONFIRMED, and worse than recorded.** `VmlWrap` has two
  fields, `mode` and `distances_twips`; `apply_element` reads `@type` only, and `@side`,
  `@anchorx` and `@anchory` are read nowhere in any crate. `vml.rs` has no reporter in its
  ~2,200 lines, so the only finding is a generic element-level `wrap` omission from the body
  catch-all, which claims full omission even though `@type` was consumed. `body.rs`'s
  `vml_anchor_at` sets `wrap_text: None` with a comment saying there is nothing to carry.
  **The worse part:** `casual-doc-layout/src/wrap_side.rs`'s `wrap_sides` ignores its
  argument and returns `BothSides` unconditionally, so `DrawingAnchor::wrap_text` is
  discarded at layout time for **every** float — DrawingML included, where import and export
  both landed with #738/#739. Its doc comment still says the model half "is landing
  separately". That seam is in a crate this lane does not own and is the single highest-value
  item left on the drawing side.

## 6. Also found, and not an import defect

Five of the owner's private documents were committed to `fixtures/corpus/` and untracked
again one commit later ("untrack private probe docs"). The blobs remain reachable in
`main`'s history. That is a confidentiality matter for the owner to decide on, not something
to fix by rewriting published history unasked.

## 7. The queue this leaves

In the order the measurement supports, each with its document frequency out of nineteen:

1. **Theme colour on the page** (5/19) — model `BorderEdge::color` as `Color` and resolve it
   at draw time. Needs the model change and a `casual-doc-layout` consumer.
2. **`wrap_sides` honours `wrap_text`** (frequency not measurable from import alone) —
   `casual-doc-layout`, and it unblocks #738/#739's already-landed import and export.
3. **`w:style@w:customStyle`** (4/19) and **`w:hyperlink@w:history`** (6/19) — a boolean
   each; model or report.
4. **`pic:cNvPr@descr`** (2/19) — alt text already round-trips on `wp:docPr`; find why the
   picture-level one does not.
5. **`w:documentProtection` crypto group** (1/19) — **DONE, as reporting.** Every
   password attribute the importer meets on `w:documentProtection` *or*
   `w:writeProtection` now raises a named `Degraded` attribute finding, so the security
   property stops vanishing in silence. Two corrections to this document's own
   enumeration: the group is **sixteen** attributes, not the seven the table at §3 lists —
   `AG_TransitionalPassword`'s `w:algorithmName`, `w:hashValue`, `w:saltValue` and
   `w:spinCount` are the ISO verifier form Office writes *instead* of the legacy group,
   and they appeared nowhere in this tree — and `w:writeProtection` carries both groups
   too and was losing them the same way. Verifying or re-emitting the hash remains
   ADR-052's open decision and is deliberately not done.
6. **`v:wrap@side`** — parse it into `VmlWrap` and carry it to `wrap_text`, matching what
   #739 did for the DrawingML side.
7. **Arm the attribute axis as a gate**, now that the reductions that make it signal rather
   than noise are written down and measured. `35` deferred it on the evidence that a
   bare-name gate was dominated by spelling; a value-aware pair-level gate is not, and the
   harness in this document is the prototype of it.
